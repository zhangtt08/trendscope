## 3. 真正的缺陷(与"谁触发了那一次"是两件事)

命名「示例数据 · <fixture.title>」只可能来自 `POST /api/import/fixture`(`server/src/routes/api.ts`)。
该端点**此前没有任何库归属检查**:无论指向演示库还是正式库,它都会把 fixture 全量写进去。
对照组 `loadDemoData()` 早就有守卫 —— 同一个产品里两个"装示例数据"的入口,一个有护栏一个没有。
这就是缺陷本身:一次点击、一个脚本、一次自动化都足以污染正式库,而且不报错。

## 4. 已做的修复

1. **端点守卫**:非演示库且未带显式确认时,`POST /api/import/fixture` 返回 409,并在错误里写清怎样才能这么做
   (`confirm: LOAD_SAMPLE_INTO_CURRENT_DB`);被拒时不产生任何写入。前端「导入中心」按钮改为带显式确认。
2. **测试进程防护**:`resolveDbPath()` 在 `VITEST` / `NODE_ENV=test` 下拒绝返回默认库路径,必须显式 `TRENDSCOPE_DB`。
3. **回归测试**:`tests/integration/http-contract.test.ts` 新增 2 例(无确认 → 409 且 `totalContent` 不变;带确认 → 200)。

## 5. 清理过程与结果

- 先 `npm run db:backup`,校验通过(表数与总行数逐项一致、`integrity ok`)后才动库。
- 删除按**库自身的外键声明**逐个找到引用 `content_items` 的子表,子表先删,再删 `content_items` → `raw_records` → `import_batches`,最后 `INSERT ... rebuild` 重建 FTS。
- 第一次尝试因外键约束**整体回滚**,不存在"删了一半"的中间状态。
- 收尾:`pragma foreign_key_check` 孤立行 **0**,`integrity_check` **ok**,内容 152 条(知乎真实 99 条),重跑 6 步全分析 completed,演示占比回到 12.1%(剩余是早期几条 QA 小样本)。

## 6. 仍未定位的部分(不假装已经查清)

- **是谁在 15:37 调用了那次示例导入**,没有证据链。应用内只有「导入中心」按钮调用该端点;
  本轮所有自建脚本都没有 POST 过 `/api/import/fixture`;使用者表示自己没有添加数据。
  服务端没有请求审计日志,因此无法回查调用来源。
- 因此**不能断言"缺陷已消除后事故不会再发生"** —— 缺陷面(无声写入)已经关闭,但触发者身份未知。

## 7. 下一步该做的两件事(尚未实现)

1. **写入库归属的可查证据**:给会改数据的端点加一条最小审计(时间、端点、批次 id、来源标记、是否演示库),
   这样下次能直接回答"谁写的"。
2. **把防护从"测试进程"升级到"只有服务器进程可用默认库路径"**:`doctor` / `db:backup` / `demo` 这类
   合法 CLI 需要显式授权(例如各自传 `TRENDSCOPE_DB` 或一个明确的 opt-in 变量),而不是共享默认路径。
   这项会动多个入口,没有在小改动里顺手做完。
